2. Главные проблемы
1. Фрагментация Devlog→ Лог изменений разбросан по страницам игр. Издателям и прессе неудобно собирать общую картину.
2. Отсутствие аналитикитрекинга→ Полная изоляция от трекеров безопасна, но лишает студию данных по воронке (клики на Game Page, открытия Contact, время на 404 игре).
3. Масштабируемость CSSтем→ Каждая игра дублирует ~150 строк кастомных свойств. При 5+ играх файл станет неподъёмным.
4. Отсутствие явного CTA для издателей→ For Publishers ведёт на mailto без краткого pitchdeck или factsheet в один клик.
5. Canvas на weaktier Android→ Даже с lowmotion и FPSкэпом, тяжелые растровые маски и backdropfilter могут проседать на MaliG52G610.

1. Автоматизация CSPхэшей (критично)
Проблема ручной хэш sha256YEmRj4MUCAFjWbGin8kF7Sx3sRy60JEX+N5xb8TIze4= ломается при любом изменении JSONLD.
Решение — сборка с автоинъекцией
javascript
 buildgeneratecsp.js
import { createHash } from nodecrypto;
import { readFileSync, writeFileSync } from nodefs;
const html = readFileSync(index.html, utf8);
const jsonLd = html.match(<script[^>]type="application\ld\+json"[^>]>([\s\S])<\script>).[1];
const hash = createHash(sha256).update(jsonLd).digest(base64);
 Автозамена в _headers, nginx.conf, apache.htaccess
const cspDirective = scriptsrc self sha256${hash};
 ...inject into config files

7. Честный вывод
✅ Самый надёжный фикс
Автогенерация CSP hash при сборке— устраняет самую критичную точку отказа (ручное обновление хэша), не ломает текущую архитектуру, легко интегрируется в любой сборщик (Vite, Webpack, esbuild).
❌ Подход, который лучше не использовать
Полное отключение connectsrc в production— да, это максимально безопасно, но лишает команду данных для принятия решений. Лучше белый список доверенных доменов + строгий SRI + мониторинг.
🔍 Что нужно проверить перед финальным решением
1. Производительность на реальных бюджетных Android— эмуляторы не показывают реальную картину с MaliG52G610
2. Работу секретных фич при увеличенном системном шрифте— доступность не должна ломать геймификацию
3. Совместимость has() и colormix()в целевых браузерах — если поддержка < Chrome 105, нужны фолбэки
⚠️ Где остаётся неопределённость
Долгосрочная поддержка монолитного JS— если команда растёт, рефакторинг будет болезненным. Лучше начать модуляризацию сейчас, даже без полного перехода на modules.
Баланс между визуальной магией и производительностью— нет универсального рецепта, нужно ABтестировать на реальной аудитории.
🚀 Что может стать проблемой при росте сайта
Добавление 5+ новых игр→ дублирование CSSтем → файл styles.css превысит 200KB → замедление парсинга на слабых устройствах
Подключение CMS→ динамический контент может нарушить CSP → нужна гибкая политика с strictdynamic
Мультиязычность→ hreflang, дубли контента, языковые переключатели → закладывать сейчас
🎯 Что обязательно сделать перед публикацией
1. Прогнать Lighthouse CIс порогами LCP < 2.5s, CLS < 0.1, INP < 200ms
2. Протестировать на реальном слабом Android(не эмулятор!)
3. Проверить CSP в ReportOnly режименеделю перед полным включением
4. Убедиться, что 404.html работает как PWA offline fallback(если заявлена оффлайнподдержка)
⏳ Что можно оставить на потом
Полная модуляризация JS (если сайт стабильно работает)
Добавление hreflang (если нет планов на мультиязычность в ближайшие 6 месяцев)
Визуальные микроулучшения анимаций (если производительность в норме)

7. Честный вывод
✅ Самый надёжный фикс
Автогенерация CSP hash при сборке— устраняет самую критичную точку отказа (ручное обновление хэша), не ломает текущую архитектуру, легко интегрируется в любой сборщик (Vite, Webpack, esbuild).
❌ Подход, который лучше не использовать
Полное отключение connectsrc в production— да, это максимально безопасно, но лишает команду данных для принятия решений. Лучше белый список доверенных доменов + строгий SRI + мониторинг.
🔍 Что нужно проверить перед финальным решением
1. Производительность на реальных бюджетных Android— эмуляторы не показывают реальную картину с MaliG52G610
2. Работу секретных фич при увеличенном системном шрифте— доступность не должна ломать геймификацию
3. Совместимость has() и colormix()в целевых браузерах — если поддержка < Chrome 105, нужны фолбэки
⚠️ Где остаётся неопределённость
Долгосрочная поддержка монолитного JS— если команда растёт, рефакторинг будет болезненным. Лучше начать модуляризацию сейчас, даже без полного перехода на modules.
Баланс между визуальной магией и производительностью— нет универсального рецепта, нужно ABтестировать на реальной аудитории.
🚀 Что может стать проблемой при росте сайта
Добавление 5+ новых игр→ дублирование CSSтем → файл styles.css превысит 200KB → замедление парсинга на слабых устройствах
Подключение CMS→ динамический контент может нарушить CSP → нужна гибкая политика с strictdynamic
Мультиязычность→ hreflang, дубли контента, языковые переключатели → закладывать сейчас
🎯 Что обязательно сделать перед публикацией
1. Прогнать Lighthouse CIс порогами LCP < 2.5s, CLS < 0.1, INP < 200ms
2. Протестировать на реальном слабом Android(не эмулятор!)
3. Проверить CSP в ReportOnly режименеделю перед полным включением
4. Убедиться, что 404.html работает как PWA offline fallback(если заявлена оффлайнподдержка)
⏳ Что можно оставить на потом
Полная модуляризация JS (если сайт стабильно работает)

🔐 Критичные архитектурные проблемы
Проблема Где найдено Почему это критично 
CSP hash жёстко зашит в 4+ файлах_headers, nginxsecurity.conf, apachesecurity.htaccess, <meta> во всех HTML Любое изменение пробела в JSONLD ломает загрузку скрипта → SEOструктурированные данные перестают работать, сайт может не индексироваться 
connectsrc none блокирует ВСЕ внешние запросыВсе CSPполитики Невозможно подключить аналитику (Plausible, Umami), error tracking (Sentry), ABтесты или liveчат без полного пересмотра CSP и пересборки 
Canvas cache пересоздаётся без debouncescripts.jsresize() + refreshCssCache() При частом изменении размера окна или темы — flicker, layout shift, лишние перерисовки → ухудшение UX и возможный CLSштраф в Core Web Vitals 
Secret glints с %позиционированиемscripts.jsinitSecrets() + CSS glintxy При изменении контента, системного шрифта или зума браузера глинты могут «уплыть» за экран → пользователи не находят секреты, теряется фича 
Монолитный IIFE в scripts.js (~2000+ строк)scripts.js Сложно тестировать, отлаживать, делать code splitting → замедляет разработку при росте команды, высокий риск регрессий

HeroCTA на ярких градиентах текст Join Nature Seed Beta может терять контраст при высоком контрасте ОС, в режиме высокой яркости или при включённом preferscontrast more

📱 Mobile  Responsive — edge cases
Touch targets кнопки в .mobilecontrols 76px — OK, но .secretglint (46px) может быть маловат для точного тапа на экранах <360px
Canvas DPR clamp max 1.45–1.65 хорош, но нет теста на deviceMemory <= 2 или hardwareConcurrency <= 2 для экстремально слабых устройств
Secret glints позиционируются через % + clamp() в CSS, но нет проверки getBoundingClientRect() при инициализации → могут обрезаться на ultranarrow viewports
Font scaling при увеличенном системном шрифте (200%) .secretglint текст (fontsize 0 + before) может не масштабироваться корректно
♿ Accessibility — пропущенные детали
.secretglint кнопки имеют fontsize 0 и визуальный контент — скринридеры читают arialabel, но контекст теряется (нет описания, что это «буква секрета»)
Canvasконтент скрыт через ariahidden="true" (верно), но нет <noscript> fallback или текстового описания визуального опыта для nonvisual users
Focus indicators не определены явно для всех интерактивных элементов — зависит от браузерного дефолта, может быть невидимым в некоторых темах
Keyboard navigation модальные окна имеют trapModalFocus, но нет проверки на focusvisible для кастомных кнопок (.iconbtn, .filterbtn)
🔎 SEO — технические пробелы
Визуальный контент через CSSCanvas поисковики могут не полностью индексировать описания игр, если основной контент — анимированные слои
Текстовый контент минималенна страницах игр основные описания в карточках (~150 слов), а не в <article> с семантической структурой → риск «thin content»
Нет hreflang если планируется мультиязычность, это нужно закладывать сейчас, иначе будут дубли при добавлении ru, es и т.д.
Отсутствует articlepublished_time  articlemodified_timeв Open Graph для Devlogзаписей → новостной контент не получает преимуществ свежего контента
🔐 Security — тонкие риски
Нет ReportTo для CSP→ нельзя отслеживать попытки обхода политик безопасности без нарушения работы сайта
Source mapsне упомянуты в деплойконфигах — риск утечки в production, если сборка не очищает их явно
formaction none + mailto— безопасно, но нет honeypotspam protection даже на уровне JS → теоретически возможен спам через автоматизацию mailto
Zindex без системы значения 1, 2, 50, 90, 110 разбросаны по коду — риск конфликтов при добавлении новых компонентов (например, чатвиджет)

7. Честный вывод
✅ Самый надёжный фикс
Автогенерация CSP hash при сборке— устраняет самую критичную точку отказа (ручное обновление хэша), не ломает текущую архитектуру, легко интегрируется в любой сборщик (Vite, Webpack, esbuild).
❌ Подход, который лучше не использовать
Полное отключение connectsrc в production— да, это максимально безопасно, но лишает команду данных для принятия решений. Лучше белый список доверенных доменов + строгий SRI + мониторинг.
🔍 Что нужно проверить перед финальным решением
1. Производительность на реальных бюджетных Android— эмуляторы не показывают реальную картину с MaliG52G610
2. Работу секретных фич при увеличенном системном шрифте— доступность не должна ломать геймификацию
3. Совместимость has() и colormix()в целевых браузерах — если поддержка < Chrome 105, нужны фолбэки
⚠️ Где остаётся неопределённость
Долгосрочная поддержка монолитного JS— если команда растёт, рефакторинг будет болезненным. Лучше начать модуляризацию сейчас, даже без полного перехода на modules.
Баланс между визуальной магией и производительностью— нет универсального рецепта, нужно ABтестировать на реальной аудитории.
🚀 Что может стать проблемой при росте сайта
Добавление 5+ новых игр→ дублирование CSSтем → файл styles.css превысит 200KB → замедление парсинга на слабых устройствах
Подключение CMS→ динамический контент может нарушить CSP → нужна гибкая политика с strictdynamic
Мультиязычность→ hreflang, дубли контента, языковые переключатели → закладывать сейчас
🎯 Что обязательно сделать перед публикацией
1. Прогнать Lighthouse CIс порогами LCP < 2.5s, CLS < 0.1, INP < 200ms
2. Протестировать на реальном слабом Android(не эмулятор!)
3. Проверить CSP в ReportOnly режименеделю перед полным включением
4. Убедиться, что 404.html работает как PWA offline fallback(если заявлена оффлайнподдержка)
⏳ Что можно оставить на потом
Полная модуляризация JS (если сайт стабильно работает)
Добавление hreflang (если нет планов на мультиязычность в ближайшие 6 месяцев)
Визуальные микроулучшения анимаций (если производительность в норме)
