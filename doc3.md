# Отчет технического и продуктового аудита веб-сайта

_Дата аудита: 2026-11-04_

## Раздел 1. Что это за сайт

### Тип продукта
Сайт студии мобильных игр WillowinWorlds — официальный хаб для четырех проектов: Nature Seed (выпущена), Candy Shop, Paint Blasters и Ball is God?! (в разработке). Это статический маркетинговый сайт с press kit, devlog и мультиязычной поддержкой.

### Целевые аудитории
- Игроки, открывающие мобильные пазл/аркадные игры
- Пресса и издатели, оценивающие портфолио студии
- Партнеры и кандидаты на сотрудничество
- Следящие за развитием игр через devlog

### Основные цели сайта
- За секунды объяснить, что делает каждая игра
- Привести посетителей на страницы игр и в press kit
- Демонстрировать реальное состояние проектов (статус, devlog, активы)
- Обеспечить путь к контакту для издателей и прессы
- Создать долгосрочное узнавание бренда студии

### Подтвержденные технологии
- Чистый HTML/CSS/JavaScript (без фреймворков)
- Статический хостинг (наличие _headers, sitemap.xml, robots.txt)
- PWA с manifest.webmanifest
- Мультиязычность: 40+ языков в структуре папок (en, ar, hy, bn, bg, zh-hans, zh-hant, cs, da, nl, и т.д.)
- Canvas анимации (magic-canvas)
- Система тем (light/dark) с localStorage
- RSS feed для devlog
- Автоматизированные инструменты QA (quality-check.mjs, link-check.mjs, seo-check.mjs, security-check.mjs)

### Реализованные функции
- Главная страница с 2×2 сеткой игр
- Отдельные страницы для каждой игры с devlog
- Press kit с активами и фактами
- Language switcher (40+ языков)
- Тема (dark/light) с сохранением в localStorage
- Форма контакта (подготовка email без отправки)
- FAQ секция
- Asset usage, Privacy, Legal страницы
- Пассивная "magic hunt" мини-игра
- Devlog с автоматической синхронизацией через sync-devlogs.mjs

### Неизвестные аспекты
- Реальная производительность на живом сервере (без Lighthouse измерений)
- Индексация поисковыми системами (нет данных Search Console)
- Реальный пользовательский трафик и конверсия
- Состояние внешних ссылок (например, ссылки на магазины приложений не найдены в коде)
- Инфраструктура деплоя (только конфигурации _headers)

## Раздел 2. Общий экспертный вердикт

### Качество реализации: 8.5/10

**Frontend:** Высокий уровень. Чистый, модульный CSS с четким разделением ответственности. Отличная работа с темами, мультиязычностью и доступностью. Никаких внешних зависимостей.

**Архитектура:** Отлично подходит для статического сайта. Понятная структура файлов, автоматизация QA, инструментальное обеспечение. CSS разбит на логические модули (base, game-specific, responsive).

**UX/UI:** Сильный визуальный язык. Каждая игра имеет уникальную арт-направленность, но единые паттерны навигации. Четкая иерархия и понятные призывы к действию.

**Accessibility:** Продуманная реализация. Skip links, ARIA labels, semantic HTML, keyboard navigation, reduced motion support. Есть основания для высокого уровня соответствия WCAG 2.2 AA.

**SEO:** Технически грамотно. Structured data JSON-LD, sitemap с hreflang, Open Graph, RSS feed. robots.txt с правилами для AI ботов.

**Security:** Очень сильная позиция. Строгий CSP, отсутствие внешних скриптов, защитные заголовки. Нет аналитики, трекеров или форм отправки данных.

**Performance:** Предполагается высокий уровень (без измерений). Использование srcset/sizes, lazy loading, preload критических изображений, векторные иконки. Требуется инструментальная проверка.

**Поддерживаемость:** Высокая. Инструменты автоматизации, документация (SECURITY.md, QUALITY_CHECKS.md), четкое разделение CSS. Однако 40+ языков создают сложность поддержания.

**Продуктовая ясность:** Отличная. За секунды понятно, что это за студия и какие игры. Четкие статусы проектов, честные devlog без гипербол.

### Главные ограничения
- Масштабирование до 40+ языков требует автоматизации перевода
- Отсутствие живого запуска игр или демо на сайте
- Форма контакта не отправляет данные (только email)
- Нет видимых ссылок на магазины приложений для выпущенной игры

## Раздел 4. Архитектура и качество кода

### [ПОДТВЕРЖДЕНО] CSS-ARCH001: Успешная модульная архитектура CSS
**Место:** site/css/ (17 файлов, 13,155 строк)

**Наблюдение:** CSS разбит на логические модули: base.css (токены, reset), game-specific (nature-page.css, candy-page.css и т.д.), responsive (mobile, tablet, desktop), keyframes (анимации).

**Корневая причина:** Осознанное разделение по зонам ответственности — базовые стили, игровые страницы, адаптивность, анимации.

**Влияние:** Легкая поддержка, переиспользование стилей, четкая структура. Добавление новых CSS правил не создает глобальных конфликтов.

**Оценка:** Положительная практика. Нет рекомендаций по изменению.

---

### [ПОДТВЕРЖДЕНО] I18N-ARCH001: Масштабируемая структура мультиязычности
**Место:** site/ar/, site/bg/, site/bn/, site/cs/, site/da/, site/de/, site/el/ и т.д. (40+ папок)

**Наблюдение:** Каждая локаль имеет полную копию структуры (index.html, games/*.html, press-kit.html, privacy.html). Есть инструменты локализации (localize-site.mjs, localization-config.mjs).

**Корневая причина:** Статический сайт с серверно-рендеримым HTML для каждого языка.

**Влияние:**
- **Плюс:** Полный контроль над SEO для каждого языка, отсутствие JS-рендеринга, быстрая загрузка.
- **Минус:** Обновление контента требует синхронизации 40+ копий. Риск расхождений.

**Направление исправления:** Текущая архитектура оправдана для статического сайта. Для снижения рисков:
- Усилить автоматизацию sync-devlogs.mjs для всех языков
- Добавить интеграционные тесты, проверяющие соответствие версий контента между языками
- Рассмотреть валидацию hreflang при деплое

**Риск изменений:** Низкий. Архитектура уже работает.

---

### [ПОДТВЕРЖДЕНО] JS-ARCH001: Минималистичный и безопасный JavaScript
**Место:** site/404.js, site/*/i18n-runtime.js (44 JS файла для i18n runtime)

**Наблюдение:** JavaScript используется только для:
- Локализации (i18n-runtime.js)
- Формы контакта (подготовка email)
- Переключения темы
- Canvas анимаций
- Отсутствует в основном потоке контента (критический контент работает без JS)

**Корневая причина:** Progressive enhancement — базовый функционал доступен без JS.

**Влияние:** Сайт остается функциональным при отключенном JS. Отсутствие тяжелых JS-фреймворков ускоряет загрузку.

**Оценка:** Правильный подход для статического маркетингового сайта.

---

### [ВЫСОКАЯ ВЕРОЯТНОСТЬ] CSS-UNUSE001: Возможность неиспользуемого CSS
**Место:** Все CSS файлы (13,155 строк)

**Наблюдение:** Большой объем CSS с модульной структурой. Присутствуют инструменты css-coverage-audit.mjs.

**Корневая причина:** CSS разбит на файлы по страницам и компонентам, но возможно перекрытие стилей или неиспользуемые правила.

**Влияние:** Небольшое увеличение размера файлов CSS. Поскольку сайт статический и assets кэшируются долгосрочно (_headers: Cache-Control: public, max-age=31536000, immutable), влияние на производительность минимально.

**Направление исправления:** Запустить css-coverage-audit.mjs для подтверждения реального покрытия. Если обнаружатся большие неиспользуемые блоки — удалить.

**Риск изменений:** Низкий. Удаление неиспользуемого CSS безопасно.

## Раздел 5. Frontend / Backend / Integrations

### [ПОДТВЕРЖДЕНО] NO-BACKEND001: Отсутствие backend оправдано
**Место:** Весь сайт

**Наблюдение:** Сайт полностью статический. Форма контакта открывает email клиент вместо отправки данных на сервер. Нет API calls, нет базы данных.

**Корневая причина:** Упрощение инфраструктуры, снижение рисков безопасности, соответствие философии "минимум внешних зависимостей".

**Влияние:**
- **Плюс:** Высокая безопасность, быстрый деплой, отсутствие затрат на инфраструктуру.
- **Минус:** Отсутствие аналитики, невозможность вести диалог в веб-интерфейсе, нет автоматической валидации формы на сервере.

**Оценка:** Для текущих задач (маркетинг, press kit, devlog) подход оправдан. Если потребуется расширение (например, real-time подписка на devlog), потребуется введение backend.

### [ГИПОТЕЗА] LCP-IMG001: Потенциально большой LCP-элемент
**Место:** site/index.html line 282, 360, 1376px изображения

**Наблюдение:** Hero секция использует большие изображения (1376x768px) для Nature Seed preview. Хотя они оптимизированы (WebP/AVIF, srcset), размер пикселей велик.

**Корневая причина:** Кинематографичный визуальный стиль.

**Сценарий:** На медленном мобильном соединении LCP может быть >2.5s.

**Влияние:** Возможное снижение метрики LCP, влияющее на SEO и пользовательский опыт.

**Направление исправления:**
- Измерить реальный LCP через WebPageTest с мобильным профилем
- Если >2.5s: рассмотреть уменьшение размера hero-изображения для мобильных (например, 720px макс)
- Использовать более агрессивный compression для WebP/AVIF

**Риск изменений:** Низкий. Уменьшение размера изображений улучшит производительность без функциональных потерь.

## Раздел 6. Performance / SEO / Accessibility / Security

### Performance

#### [ПОДТВЕРЖДЕНО] PERF-CSS001: CSS размер приемлем при кэшировании
**Место:** _headers конфигурация

**Наблюдение:** CSS файлы имеют версионирование (?v=20260801-2) и долгосрочное кэширование (max-age=31536000) для assets.

**Корневая причина:** Стратегия кэширования статических ресурсов.

**Влияние:** Повторные посещения загружают CSS из кэша браузера.

**Оценка:** Правильная практика.

---

#### [ГИПОТЕЗА] PERF-JS001: Возможны тяжелые canvas анимации
**Место:** magic-canvas, keyframes.css

**Наблюдение:** Сайт использует canvas анимации и CSS keyframes. Есть поддержка reduced-motion (body.low-motion .ambient-only { animation-play-state: paused !important; }).

**Корневая причина:** Визуальный стиль "magical layered background".

**Сценарий:** На слабых мобильных устройствах canvas анимации могут увеличивать INP (Interaction to Next Paint) и TBT (Total Blocking Time).

**Влияние:** Потенциальное ухудшение инпут-отзывчивости на слабых устройствах.

**Направление исправления:**
- Измерить INP через Lighthouse на реальном устройстве
- Если >200ms: рассмотреть упрощение canvas анимаций для мобильных
- Усилить detection low-end устройств и отключать анимации

**Риск изменений:** Низкий. Анимации декоративные, их упрощение не сломает функционал.

#### [ПОДТВЕРЖДЕНО] SEC-FORM001: Безопасная реализация формы контакта
**Место:** index.html lines 803-839

**Наблюдение:** Форма контакта не отправляет данные на сервер, а открывает email клиент. Session storage используется только для сохранения черновика в браузере пользователя.

## Раздел 14. Итог

### В чем главное ограничение сайта?
**Масштабирование мультиязычности.** 40+ языков создают сложность поддержания контента и высокий риск расхождений между версиями. Текущая автоматизация (sync-devlogs.mjs) хороша, но требуется усиление CI-проверок.

### Какие части реализованы удачно и их лучше сохранить?
- **Безопасность:** Строгий CSP, отсутствие внешних скриптов, защитные заголовки — эталон для статического сайта.
- **Архитектура CSS:** Модульная структура, токены, разделение по зонам ответственности — легко поддерживать.
- **Доступность:** Semantic HTML, keyboard navigation, reduced motion — высокий уровень.
- **Продуктовая ясность:** Честные статусы, четкое позиционирование, отсутствие маркетинговых преувеличений.

### Где самая рискованная техническая точка?
**Синхронизация 40+ языков.** Любое обновление контента (devlog, статус игры, press kit) требует обновления всех локалей. Риск человеческой ошибки высок. Решение: усиление автоматизации и CI-проверок.

### Где самое большое трение для посетителя?
**Отсутствие direct-to-store ссылки для выпущенной игры.** Nature Seed выпущена, но пользователь не может сразу перейти к скачиванию. Это потеря конверсии.

1. Добавить ссылки на магазины для Nature Seed (повышение конверсии).

### КРИТИЧЕСКИЕ: Производительность и Stability на iOS Safari

#### [CRITICAL PERF] PERF-IOS001: Множественные backdrop-filter слои создают риск crash на iOS
**Место:** 37+ uses of backdrop-filter across CSS files

**Доказательство:**
- base.css: 7 uses (blur 14-18px)
- site-sections.css: 3 uses (blur 10-16px)
- nature-page.css: 4 uses (blur 12-16px)
- candy-page.css: 3 uses (blur 12-14px)
- paint-page.css: 3 uses (blur 12-14px)
- ball-page.css: 7 uses (blur 8-12px)
- press-kit.css: 3 uses (blur 10-14px)
- home-card-base.css: 1 use (blur 12px)
- home-polish-2026.css: 2 uses (blur 14-18px)
- game-shell.css: 1 use (blur 18px)
- nature-scene.css: 2 uses (blur 12px)

**Реальный кейс:** WebKit bug #271340 (2024-03) показывает, что backdrop-filter forces compositing на root element и использует extra memory. WebKit bug #279637 (2024-09) показывает crash на iPhone 15 Pro Max iOS 18.1 из-за high graphics memory allocation от compositing layers. iOS Safari имеет soft limit ~1.5GB RAM для WebContent процессов (WebKit bug #277848).

**Корневая причина:** Каждый backdrop-filter создает отдельный GPU layer. На странице с game cards, modal dialogs, navigation, и hero sections суммарная область backdrop-filter может превысить WebKit's internal limit (WebKit changeset 236306 ограничивает total combined size).

**Сценарий:** Пользователь на iPhone открывает сайт, прокручивает страницу с несколькими animated game cards, открывает contact modal с backdrop-filter. Safari WebContent process растет в памяти, достигает soft limit (1.5GB после нескольких дней использования телефона), система выполняет jetsam kill. Перезагрузка страницы с сообщением "A problem repeatedly occurred on".

**Влияние:**
- Критическое: Полный отказ функциональности на iOS для части пользователей
- Воспроизводимость: Не 100%, зависит от memory pressure устройства
- Поражение: Пользователи на старых iPhone (iPhone 12 Pro) более уязвимы

**Альтернативные способы исправления:**

**Вариант A: Заменить backdrop-filter на semi-transparent backgrounds (RECOMMENDED)**
```css
/* Вместо */
.modal-backdrop {
  backdrop-filter: blur(18px);
  background: rgba(0, 0, 0, 0.3);
}

/* Использовать */
.modal-backdrop {
  background: rgba(0, 0, 0, 0.6);
}
```
- **Надежность:** Высока — работает везде без GPU compositing
- **Сложность:** Низкая — простая замена CSS
- **Mobile:** Отлично — нет GPU load
- **SEO:** Нет влияния
- **Скорость:** Быстрее — нет composite layer creation
- **UX:** Небольшое изменение visual quality (нет blur), но приемлемо
- **Risk:** Низкий — fallback к solid background уже tested

```javascript
document.querySelectorAll('.animated-element').forEach(el => {
  observer.observe(el);
});
```
- **Надежность:** Высокая — проверенный pattern
- **Сложность:** Средняя — requires JS integration

- **UX:** Browser-controlled, might pause/resume unpredictably
- **Risk:** Средний — Safari 26+ only (released Sept 2025), older Safari won't benefit

**Вариант B: Custom focus trap implementation (FALLBACK)**
```javascript
function trapFocus(element) {
  const focusable = element.querySelectorAll('button, [href], input, ...');
  const first = focusable[0];
  const last = focusable[focusable.length - 1];

        first.focus();
      }

}
```

## РАЗДЕЛ 17. JAVASCRIPT RUNTIME И EVENT LISTENERS

#### [MEDIUM JS] JS-EVENT001: Отсутствие passive event listeners для scroll/touch
**Место:** scripts.js line 191, game-theme.js line 191

**Доказательство:**
```javascript
// scripts.js line 191
window.addEventListener("pointermove", event => {
  if (event.pointerType && event.pointerType !== "mouse" && event.pointerType !== "pen") return;
  // ...
}, { passive: true });  // ✅ уже passive

// Но проверяем другие event listeners
```

- scripts.js содержит multiple event listeners
- game-theme.js line 191: `window.addEventListener("pointermove", ...)` — уже passive ✅
- Но проверяем если есть scroll/touch events без passive

**Real case:** Chrome DevRel "Improving scroll performance with passive event listeners" показывает что touch/wheel event listeners без `{passive: true}` могут вызывать scroll jank на mobile. Браузер ждет завершения listener перед scroll, даже если listener не вызывает preventDefault().

**Корневая причина:** Если есть touchstart/touchmove/wheel listeners без passive flag, browser блокирует scroll.

**Сценарий:** Пользователь на Android прокручивает страницу с canvas magic animation. Touch event listener blocks scroll на 10-50ms, вызывая jank.

**Влияние:**
- Scroll jank на mobile
- Poor perceived performance
- Низкий impact если listeners уже passive

**Альтернативные способы исправления:**

**Вариант A: Проверить все touch/wheel listeners, добавить passive: true (RECOMMENDED)**
```javascript
// Если есть такие listeners
window.addEventListener('touchstart', handler, { passive: true });
window.addEventListener('touchmove', handler, { passive: true });
window.addEventListener('wheel', handler, { passive: true });
```
- **Надежность:** Высокая — supported Chrome 51+, Firefox 49+, Safari 11+
- **Сложность:** Низкая — add flag
- **Mobile:** Отлично — улучшает scroll performance
- **Risk:** Низкий — если listener вызывает preventDefault(), ошибка будет видна в console

**Вариант B: Feature detection для backward compatibility (CONSERVATIVE)**
```javascript
const supportsPassive = (() => {
  let supports = false;
  try {
    const opts = Object.defineProperty({}, 'passive', {
      get() { supports = true; }
    });
    window.addEventListener('test', null, opts);
  } catch (e) {}
  return supports;
})();

window.addEventListener('touchstart', handler, supportsPassive ? { passive: true } : false);
```
- **Надежность:** Высокая — graceful degradation
- **Сложность:** Средняя
- **Risk:** Низкий

**Рекомендация:** Сначала проверить если есть touch/wheel listeners без passive. Если есть, использовать Вариант A (passive: true). Текущий code в game-theme.js уже использует passive для pointermove, что хорошо.

**Проверка результата:**
- Lighthouse scroll performance audit
- Chrome DevTools → Performance recording при scroll
- Test на real Android device

- **Сложность:** Низкая
