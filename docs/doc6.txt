**Раздел 1. Что это за сайт**

**Тип продукта (подтверждено):** статический многоязычный сайт игровой студии WillowinWorlds (портфолио + пресс-кит + информационные страницы). Не SaaS, не магазин, не веб-приложение с бэкендом. Основной контент — презентация четырёх мобильных игр (Nature Seed — выпущена; Candy Shop, Paint Blasters, Ball is God?! — в разработке), пресс-материалы, политика активов, legal/privacy, контакт через mailto.

**Целевые аудитории и сценарии:** издатели, пресса, потенциальные партнёры/кандидаты, игроки, интересующиеся студией. Ключевые действия: изучить игры и статус, скачать превью-ассеты, отправить запрос (контакт/пресс/портфолио), переключиться на свой язык.

**Стек (подтверждено из экспорта):** чистый HTML + CSS + vanilla JS (IIFE), никаких React/Vue/Next и т.п. Canvas-анимации (главная «magic» сцена + 404-мини-игра), localStorage/sessionStorage, matchMedia, picture/srcset/AVIF/WebP, строгий CSP, nginx-конфиги для заголовков безопасности и кэша. Обширная i18n: отдельные HTML-страницы по локалям + `i18n-runtime.js` + language-switcher. Нет серверного кода, API, БД, аналитики, cookies-трекинга, аккаунтов.

**Что подтверждено:** статический хостинг, отсутствие сторонних скриптов/пикселей, mailto-формы с черновиком в sessionStorage, тема (light/dark) с localStorage, адаптивное качество canvas (low-data / reduced-motion / small screen), focus management + inert + Escape для модалок, sitemap с hreflang, robots, manifest, security.txt (упоминается), 404 как полноценная canvas-игра с обработкой спрайтов.

**Что предполагается:** деплой через nginx (есть конфиги), генерация локалей/sitemap частично автоматизирована (есть `update-sitemap-lastmod.mjs`).

**Что неизвестно без запуска/измерений:** реальные Core Web Vitals, фактическая индексация, поведение на реальных устройствах, полнота всех локалей, наличие build-пайплайна за пределами экспорта, точный список всех ассетов.

**Раздел 2. Общий экспертный вердикт**

Это один из самых технически зрелых и дисциплинированных статических сайтов студии, которые встречаются в практике небольших команд. Frontend-качество высокое (особенно canvas-логика, lifecycle, адаптивность под сеть/motion, focus/inert в модалках). Архитектура — «статический сайт с сильным client-side polish». Security posture выдающийся для маркетингового сайта (строгий CSP, почти нулевая поверхность атаки, нет third-party). Accessibility заложена серьёзно. SEO-фундамент (hreflang, canonical, sitemap, OG) сильный.

Главные ограничения — экстремальная дубликация контента по ~40 локалям (стоимость владения) и mailto-only контакт (трение и отсутствие обратной связи). Production-ready как статический пресс/портфолио-сайт — да, при условии контроля дрифта локалей и измерения перформанса.

Оценки (где данных достаточно):
- Frontend / JS-качество: 8.5–9
- Security / privacy posture: 9+
- Accessibility foundations: 8
- SEO foundations: 8.5
- Поддерживаемость / cost of ownership: 5–6 (из-за локалей)
- Продуктовая ясность: 8
- Performance: недостаточно данных для оценки (нужны измерения)

**Раздел 3. Критические и блокирующие проблемы**

Подтверждённых P0 (потеря данных, критический сбой основных сценариев, серьёзные уязвимости) **нет**.

P1-кандидаты (требуют проверки/устранения в первую очередь):

**WEB001 / A11Y001 — Language switcher (огромный `<details>` с 40+ ссылками)**
Место: почти все страницы, блок `language-switcher`.
Наблюдение: длинный список локалей внутри одного `<details>`.
Риск: плохая usability на мобильных, возможные проблемы с focus order / screen readers при открытии, лишняя нагрузка на DOM.
Приоритет: P1–P2.
Направление: сгруппировать (регионы), поиск, или progressive disclosure; проверить keyboard + SR.

**WEB002 — Mailto-only контакт**
Место: `scripts.js` (submit → `window.location.href = draft.href`), все локали.
Наблюдение: форма только готовит mailto; нет серверной отправки, нет подтверждения доставки, зависит от клиента пользователя.
Последствие: потеря части запросов (мобильные без настроенного mail-клиента, корпоративные ограничения).
Приоритет: P1 с продуктовой точки зрения.
Альтернативы: Formspree/Getform/Netlify Forms (минимальный), или простой serverless endpoint + уведомление; оставить mailto как fallback.

**WEB003 — Дублирование контента по локалям**
Место: вся структура `site/{locale}/...` + корневые страницы.
Наблюдение: почти полный HTML-дубль на каждую локаль.
Риск: дрейф переводов, забытые обновления, рост размера репозитория/деплоя, сложность правок.
Приоритет: P1 (поддерживаемость).
Направление: вынести общий контент в шаблоны/генерацию (даже простой SSG или build-скрипт), оставить только переводимые строки.

Остальные найденные проблемы ниже — P2/P3 или гипотезы.

**Раздел 4. Архитектура и качество кода**

Плюсы:
- Чистое разделение: `scripts.js` (главная интерактивность + canvas), `game-theme.js` (темы + фильтры + mascot), `404.js` (изолированная игра), per-locale `i18n-runtime.js`.
- Хороший lifecycle: visibilitychange, pagehide/pageshow (404), reduced-motion / saveData / effectiveType, requestAnimationFrame с throttling.
- Состояние модалок централизовано, focus restore + trap + inert.
- Нет глобального загрязнения; IIFE, осторожная работа с storage (try/catch).

Минусы / долг:
- Сильная связанность через DOM-селекторы и data-атрибуты (типично для vanilla).
- Дублирование HTML/логики между локалями — главный архитектурный риск.
- Canvas-логика в `scripts.js` и `404.js` довольно плотная; поддерживаема, но при росте лучше выносить утилиты (математика, particles, quality tiers).
- Нет видимых unit/integration-тестов в экспорте.

**Раздел 5. Frontend / Backend / Integrations**

Backend отсутствует — это осознанный выбор (низкая поверхность атаки). Интеграции только mailto и статические ассеты.

Frontend-сильные стороны:
- 404-игра: flood-fill удаление фона спрайтов, trim, аккуратный spawn/difficulty, combo, effects, mobile controls, pause on visibility — уровень выше типичного «пасхального яйца».
- Главная canvas-сцена: адаптивное качество, background cache, reduced-motion path.
- Модалки: корректный focus trap, inert на фоне, Escape, restore focus.
- Форма контакта: черновик в sessionStorage, copy-to-clipboard fallback, reportValidity.

Потенциальные дефекты / риски:
- В 404.js обработка спрайтов через getImageData + flood-fill — CPU-heavy при первой загрузке (особенно на слабых устройствах). Есть once-listener, но стоит измерить.
- `pointerX` / keyboard / touch — логика управления в 404 аккуратная, но стоит проверить edge-cases при смене orientation / resize во время игры.
- Language switcher и огромные списки hreflang в sitemap — возможны проблемы с размером/парсингом.

**Раздел 6. Performance / SEO / Accessibility / Security**

**Performance**
Механизмы mitigation есть (low-data class, reduced-motion, particleCount scaling, AVIF/WebP + srcset, lazy, fetchpriority на LCP-кандидатах).
Риски: тяжёлая canvas + много изображений на главной и press-kit; flood-fill в 404; большие language-switcher DOM.
Нужны измерения: Lighthouse/WebPageTest на mid-range Android + slow 4G, DevTools Performance на canvas loop, memory при долгом idle.

**SEO**
Сильный фундамент: canonical, robots, sitemap с hreflang, OG/Twitter, content-language, noindex на 404.
Риски: возможный дрейф между локалями, очень большой sitemap, зависимость от правильного деплоя trailing-slash/www.
Не утверждаю индексацию — нужна Search Console.

**Accessibility**
Хорошие практики: role=dialog + aria-modal, labelledby, focus restore, trap, inert + aria-hidden на фоне, skip-link, aria-live на части статусов, prefers-reduced-motion.
Точки внимания: language switcher (длинный список), контраст в некоторых градиентах/иконках (нужна проверка), touch targets в мобильных controls 404, полнота alt/aria на декоративных изображениях (многие корректно пустые/aria-hidden).

**Security / Privacy**
Один из лучших аспектов:
- Строгий CSP (default-src 'self', connect-src 'none', form-action 'none', frame-ancestors 'none', trusted-types и т.д.) + nginx-заголовки (HSTS, COOP, CORP, Permissions-Policy, X-Frame-Options DENY и др.).
- Нет third-party скриптов, аналитики, трекинговых cookie.
- Черновики только в sessionStorage (та же вкладка).
- Privacy/legal/asset-usage страницы явные.

Риски низкие. Единственное — CSP-hash должен оставаться в синхронизации с любыми inline/изменяемыми скриптами; при изменении JS нужно обновлять hash.

**Раздел 7. UI/UX и продуктовый анализ**

Ясность сильная: «Small games. Living worlds.», сразу виден портфель из четырёх игр со статусами, пресс-кит и контакт доступны.
Иерархия: hero → games grid с фильтрами → press/facts → contact.
Хорошо различимы released vs in-development.
Трение: mailto-форма и необходимость открывать почтовый клиент; огромный language switcher может отпугивать.
Пресс-кит и asset policy продуманы (preview-level, credit, no AI training / resale).
Без живого браузера/скриншотов нельзя полностью оценить визуальную плотность и mobile hierarchy, но код показывает осознанную работу с адаптивностью и motion.

**Раздел 14. Итог**

**Главное ограничение:** стоимость поддержки из-за почти полного HTML-дублирования по десяткам локалей + зависимость контакта от mailto.

**Что сделано удачно и стоит сохранить:** строгий security/privacy posture, качество canvas-кода и lifecycle, focus/inert/Escape в модалках, адаптивное качество под сеть и motion, пресс-кит и asset policy, 404 как полноценный мини-опыт.

**Самая рискованная техническая точка:** рассинхрон CSP и рост сложности поддержки локалей.

**Самое большое трение для посетителя:** контакт через mailto и потенциально перегруженный language switcher.

**3–5 действий с наибольшим эффектом:**
1) измерения перформанса,
2) улучшение доставки контактов,
3) снижение дублирования локалей,
4) доработка language switcher,
5) формализация процесса CSP/sitemap.

**Что не стоит переписывать:** весь стек на фреймворк, отказ от строгого CSP, отказ от статического подхода — он здесь сильная сторона.

**Следующий рациональный этап:**
- Зафиксировать baseline Performance + a11y.
- Улучшить contact.
- Начать генерацию общих частей, чтобы локали перестали быть ручным копипастом.
- Только после этого — расширение функциональности (store links, playable previews и т.д.).

Отчёт основан исключительно на предоставленном экспорте. Для финальных решений по перформансу, реальной индексации и визуальной плотности на устройствах нужны инструментальные проверки в браузере.
**Дополнение к аудиту — важные пробелы и уточнения**

Ниже — то, что стоит дописать к предыдущему отчёту. Это не повтор, а недостающие акценты, которые влияют на приоритеты.

### 1. Критичные технические детали, которые раньше были недостаточно раскрыты

**404-игра (`404.js`) — сильная реализация, но с рисками первого запуска**

- Обработка спрайтов через `getImageData` + flood-fill + trim выполняется при загрузке каждого изображения. Это CPU-тяжёлая операция на главном потоке.
- На слабых Android / старых iPhone при первом заходе возможна заметная задержка перед стартом игры или дёрганье.
- Статус: **[ВЫСОКАЯ ВЕРОЯТНОСТЬ]** PERF + UX.
- Рекомендация: вынести обработку в `OffscreenCanvas` + Worker (если поддерживается) или делать lazy/on-demand только для нужных спрайтов. Как минимум — показывать простой loading-state, пока `sprites` не готовы.
- Также: `processSprite` обновляет preview-изображения через `toDataURL` — лишняя работа, если preview уже в HTML.

**Модалки и фокус — в целом хорошо, но есть краевые случаи**

- Есть `trapModalFocus`, `inert`, восстановление фокуса, Escape — это выше среднего.
- Риск: при быстром открытии нескольких модалок подряд (или клике по фону + Escape) возможны гонки с `active*Trigger`. Код старается закрывать предыдущие, но стоит явно протестировать цепочку «открыл Contact → открыл другой info-modal → Escape».
- Language switcher на базе `<details>` — удобно, но при 40+ языках на мобильном это тяжеловато и для скринридеров, и для пальца.

**Контактная форма**

- Черновик в `sessionStorage` — хорошее решение.
- Полностью зависит от `mailto:`. На многих мобильных устройствах и в корпоративных средах это приводит к потере лидов.
- Нет никакой серверной фиксации факта попытки отправки. Даже простой beacon/лог «форма была заполнена» уже повысил бы видимость.

### 2. Поддерживаемость и масштабирование (главный скрытый риск)

Это самый важный пункт, который нужно держать в голове:

- Почти полный дубль HTML по ~40 локалям.
- Любое изменение текста, структуры модалки, футера, CTA, статуса игры требует правок во многих файлах.
- Риск дрейфа переводов уже виден в отдельных локалях (машинный оттенок формулировок).
- При добавлении новой игры или изменении press-kit стоимость поддержки растёт почти линейно.

**Вывод:** пока сайт небольшой — терпимо. Как только появится 5–6-я игра или регулярные обновления статусов — начнёт сильно тормозить. Лучшее вложение сейчас — начать вынос общих частей (head, footer, modals shell, language switcher) в генерацию, даже если пока оставить контент страниц ручным.

### 3. Продуктовые и конверсионные пробелы

- Нет явного «что делать дальше» после просмотра игры в разработке (кроме «Request update»). Можно усилить: «Notify me when available» (даже через тот же mailto с предзаполненным типом).
- Пресс-кит и asset policy сделаны очень правильно и аккуратно. Это конкурентное преимущество — сохранять и подчёркивать.
- Секретный promo-hunt — милый и в духе студии. Но claim полностью ручной. Это нормально на текущем этапе, просто не стоит ожидать от него масштаба.
- Нет видимых store-ссылок (логично, пока игры не везде вышли). Когда появятся — лучше сразу делать их очень заметными и с UTM/пометками источника.

**Раздел 3. Критические и блокирующие проблемы**

Подтверждённых P0 нет.

**P1-проблемы:**

**WEB001 / A11Y001 — Language switcher**
Место: почти все страницы, блок `language-switcher` на базе `<details>`.
Наблюдение: 40+ языков в одном длинном списке.
Риск: плохая usability на мобильных, возможные проблемы с focus order и screen readers.
Приоритет: P1–P2.
Направление: группировка по регионам + поиск или progressive disclosure.

**WEB002 — Mailto-only контакт**
Место: `scripts.js` (submit → `window.location.href = draft.href`).
Наблюдение: форма только готовит mailto. Нет серверной доставки и подтверждения.
Последствие: потеря части запросов (мобильные без mail-клиента, корпоративные ограничения).
Приоритет: P1.
Направление: лёгкий serverless/form-сервис + mailto как fallback.

**WEB003 — Дублирование контента по локалям**
Место: вся структура `site/{locale}/...`.
Наблюдение: почти полный HTML-дубль.
Риск: дрейф переводов, высокая стоимость любых правок, рост репозитория.
Приоритет: P1 (поддерживаемость).
Направление: вынос общих частей (head, footer, modals, switcher) в генерацию.

**PERF001 — Холодный старт 404-игры**
Место: `404.js`, `processSprite` + flood-fill + `getImageData` + `toDataURL`.
Наблюдение: тяжёлая обработка спрайтов на главном потоке при загрузке.
Риск: заметная задержка/джank на слабых устройствах при первом заходе.
Приоритет: P1.
Направление: loading-state + по возможности OffscreenCanvas/Worker или lazy-обработка.

Сейчас у вас один из самых технически зрелых и дисциплинированных сайтов в своём классе (особенно CSP, отсутствие трекеров, 404-игра, мультиязычность, press-kit).
Слабее — в эмоциональной ясности «кто мы», доказательстве traction и удобстве конверсии (контакт + следующие шаги).

### Что добавить / улучшить (по приоритету)

### 1. Критично и срочно (сделать в первую очередь)

- **Исправить доменный рассинхрон**
  Все canonical, og:, sitemap, robots.txt и email сейчас указывают на несуществующий `willowinworld.com`. Это главный блокер SEO и доверия. Привести всё к `willowinworlds.com`.

- **Сделать контакт реально рабочим**
  Сейчас только mailto. Добавить простой надёжный канал (Formspree / Getform / Cloudflare Workers / Netlify Forms) + оставить mailto как fallback. Это сильно повысит конверсию от издателей и прессы.

### 2. Высокий приоритет (следующий слой)

**A. Усилить «кто мы» и доверие**
- Короткий блок «About the studio» на главной (2–4 предложения + фото/аватар основателя или команды, если есть).
- Ясный текущий фокус: «Сейчас главный приоритет — Nature Seed + развитие Candy Shop».
- Если есть реальные цифры (скачивания Nature Seed, рейтинги, пресса) — показать их скромно, но заметно.

**B. Улучшить страницы игр**
- Более сильные короткие геймплей-лупы (GIF или очень короткие видео) прямо в карточках.
- Чёткий статус + следующий шаг:
  - Released → «Play now» + ссылки на сторы
  - In development → «Wishlist / Notify me» + «Request build / press access»
- Для Nature Seed — отдельный акцент на уникальности (draw-to-solve + восстановление природы).

**C. Language switcher**
- Сейчас слишком длинный. Сделать группы (Europe / Asia / Americas) или поиск. Это заметно улучшит мобильный UX.

### 3. Средний приоритет (сделает сайт заметно сильнее)

- **Devlog / Updates**
  Лента обновлений (хотя бы раз в 1–2 месяца). Даже короткие посты сильно повышают ощущение «живая студия».

- **Press kit 2.0**
  - Одна кнопка «Download full press kit (ZIP)»
  - Готовые цитаты / factsheet в тексте
  - Высококачественные key art + вертикальные скриншоты под сторы

- **Социальное доказательство**
  - Логотипы/упоминания прессы (если есть)
  - Короткие цитаты игроков или прессы
  - Счётчик или статус «Nature Seed — released September 2026»

- **404 и интерактив**
  404-игра уже сильная. Можно добавить лёгкий «easter egg» на главной (как секретный promo-hunt), чтобы усиливать характер студии.

### 4. Что можно не делать (или делать осторожно)

- Не превращать сайт в тяжёлый блог или новостной портал.
- Не добавлять агрессивную аналитику и трекеры — текущая privacy-позиция является конкурентным преимуществом.
- Не усложнять навигацию. Сейчас она достаточно чистая.
